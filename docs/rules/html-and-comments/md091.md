# MD091: Markdown syntax inside HTML blocks

Status: implemented for CommonMark and GFM analysis.

Area: [Html and comments](index.md).

## Behavior

Report Markdown emphasis, link, or heading candidates inside raw HTML blocks that the selected parser leaves literal. Inline HTML surrounding parsed Markdown is exempt.

Inspect the selected parser's actual HTML block payload, including eligible
closing-line tails. Preserve tags and attributes, comments, processing
instructions, declarations, CDATA, and literal `script`, `style`, `pre`, and
`textarea` interiors. Parsed code, frontmatter and image alternatives are
excluded. HTML block boundaries come from the parser, rather than inferred
matching container tags.

The initial candidate grammar is deliberately bounded to one physical body
line and contiguous original payload. It includes flat emphasis with matching
maximal `*` or `_` runs of width one or two and CommonMark delimiter flanking,
flat nonblank `[label](destination)` links (including empty destinations), and
ATX headings with one through six opening hashes after at most three ASCII
spaces (including empty headings). Odd original backslashes escape markers;
triple or mixed emphasis runs are not split. Links exclude nested brackets,
titles, balanced or angle destinations, whitespace in destinations and reference
forms. No reference or resource resolution is performed.

Complete same-line matched backtick runs and flat images protect their contents.
Unmatched backtick runs are barriers; raw fence-looking lines do not create code
blocks. Tags, source gaps, transformations, physical endings and control barriers
prevent pairing. Unsupported forms, including Setext and GFM-only syntax, do not
add candidate classes. A recognized outer candidate consumes its full extent;
an ATX candidate consumes its physical line, so nested markers do not duplicate
findings. Recognition precedes directive suppression and inspection focus.

Report only the opening delimiter with
`Markdown syntax is literal inside this HTML block.` Unknown required named HTML
token boundaries withhold the complete inventory with reduced coverage. A known
unclosed opaque token or raw interior remains protected; an impossible tag-name
boundary such as the colon in `<https://x>` does not create uncertainty.

## Configuration

Default enablement: Disabled; enable explicitly for projects that require this check.

No rule-specific options.

All rules also accept the [shared settings](../index.md#configuration-and-findings). The defaults here are the planned mdchk contract.

## Examples

Violating input:

````markdown
<div>
**Guide**
</div>
````

Accepted input:

````markdown
<div>
<strong>Guide</strong>
</div>
````

Angle-bracket placeholders such as `<SPACE>`, `<TAB>`, `<EOF>`, and `<NEWLINE>` describe source characters rather than literal Markdown. Prose examples describe cases that cannot be represented directly in a UTF-8 document.

## Correction policy

Report only; switching markup or inserting blank lines changes HTML interpretation.

Any correction must satisfy the [shared preservation contract](../index.md#implementation-contract). Report remaining findings after checking the corrected document again.

## Validation

Cover the examples, every option, protected content, nested containers, LF and CRLF input, and precise diagnostic ranges. For corrections, verify preserved meaning and a second fix run with no further changes.
