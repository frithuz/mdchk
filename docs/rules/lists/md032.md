# MD032: Blank lines around lists

Status: analysis, configuration and correction implemented for CommonMark and GFM.
Eligible findings get a blank-line insertion through `fix`; the deferral cases in
the Correction policy stay manual with `fix_available: false`.

Area: [Lists](index.md).

## Behavior

Require at least one blank body line between a list and each adjacent non-list
source block in the same Document, BlockQuote or ListItem body. In a ListItem body
only, a list directly after the item's first block needs no blank line before it
when that first block is a paragraph or heading. A retained reference definition
counts as a first block, and it isn't exempt. Later paragraphs and all other blocks
in an item keep the requirement, as does the side after the list. Actual recognized
reference definitions participate even though absent from rendered children.
First and last source participants are exempt on their container-edge side.
Adjacent List groups are exempt, including changes of bullet, type or delimiter.
ListItem wrappers and lazy item continuations do not create outside neighbors.

A blank body line contains only ASCII spaces or tabs after removing actual
**enclosing parent** container prefixes. The target list's markers and deeper
container prefixes remain content. List-owned trailing blanks can separate a
following block even inside the List span. Empty final markers, definition source
and internal code/HTML/quote blanks cannot become outside separators. A terminal
line ending does not create a phantom blank line. This rule imposes no item-spacing
or tightness requirement.

Each missing side produces one zero-width original-source point: before, at the
first actual list-item marker; after, at the following non-list source block's
first physical body start after enclosing parent prefixes. For `Text\n- One`,
the point is [5,5), line 2 column 1; for `- One\n# H`, [6,6), line 2 column 1.
These are diagnostic anchors, not executable insertion instructions. Full source
context is established before suppression at the selected point's start.

## Configuration

Default enablement: Enabled.

No rule-specific options.

All rules also accept the [shared settings](../index.md#configuration-and-findings). The defaults here are the planned mdchk contract.

## Examples

Violating input:

````markdown
Text
- One
````

A list after any other first block in an item keeps its finding, here at line 4,
column 3:

````markdown
- ```
  x
  ```
  - nested
````

Accepted input:

````markdown
Text

- One
````

A nested list directly after its parent item's leading text is also accepted:

````markdown
- a
  - nested
````

Angle-bracket placeholders such as `<SPACE>`, `<TAB>`, `<EOF>`, and `<NEWLINE>` describe source characters rather than literal Markdown. Prose examples describe cases that cannot be represented directly in a UTF-8 document.

## Correction policy

`mdchk fix` inserts one blank body line on the missing side of each finding.
Before a list, the line goes at the start of the line holding the first item
marker. After a list, it goes at the start of the line holding the following
block. The inserted line repeats that line's enclosing parent container
prefixes, with trailing whitespace removed, followed by the previous line's
ending. So `Text<NEWLINE>- One` becomes `Text<NEWLINE><NEWLINE>- One`, a quoted
`> Text<NEWLINE>> - One` gets a `>` line between them, and CRLF input gets a
CRLF line.

The correction is accepted only when a reparse of the whole candidate shows the
same blocks: every list keeps its items, nesting, markers, contents and
tightness, no paragraph, list or quote splits or merges, and no byte outside the
inserted lines changes. These findings stay manual, with `fix_available: false`:

- a finding between two blocks of an item in a tight list, because the new line
  would make the list loose
- a finding whose container prefix holds anything other than spaces and `>`
  markers, such as a tab
- a list directly after an HTML block, such as a comment, because the line
  ending the new line would follow belongs to that protected block
- a finding in a directive interval or protected context, or in a document that
  opens with an unrecognized `---` or `+++` block

Any correction must satisfy the [shared preservation contract](../index.md#implementation-contract). Report remaining findings after checking the corrected document again.

## Validation

Cover the examples, every option, protected content, nested containers, LF and CRLF input, and precise diagnostic ranges. For corrections, verify preserved meaning and a second fix run with no further changes.
