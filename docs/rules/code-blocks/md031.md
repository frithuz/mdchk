# MD031: Blank lines around fenced blocks

Status: analysis and configuration implemented for CommonMark and GFM. Findings
are manual; automatic correction remains future work.

Area: [Code blocks](index.md).

## Behavior

Require an immediately adjacent blank body line before and after each actual
fenced code block, except at the first or last source participant in its owning
Document, BlockQuote or ListItem body. A list groups items; separate items do not
borrow each other's neighbors. Retained reference definitions count as source
participants, including duplicate and multiline definitions. A recognized opaque
header is outside the root body, so the first fence after it has no before
requirement.

Blank means empty or only ASCII SPACE/TAB after the actual owning-container and
ancestor prefixes. A deeper quote/list marker is content, not a removable prefix
in its parent's comparison. Immediate blanks supply separation; a distant blank
or a blank retained inside an opaque neighbor does not. Terminal list content
floors allow genuine trailing list blanks to separate the next outer block;
quotes and opaque blocks retain their full boundaries. Extra blanks do not
violate MD031.

Both backtick and tilde fences qualify, regardless of language or payload.
Normally unclosed fences end at their actual document/container boundary; no
closing fence or after-side finding is invented. Indented code, inline code,
fence-looking literal payload, recognized metadata, HTML-owned spelling, actual
raw lifetimes and whole Images are not independent targets. Raw ownership uses
the parser's actual context rather than a separate HTML or Markdown grammar.

Each missing side has its own zero-width original insertion point. Before is at
the opener's physical line start after actual ancestor prefixes and before the
fence's optional indentation. After is at the closing line's content end,
including trailing padding and before its whole line ending. CRLF is never
split; TAB remains one source byte/public column. Adjacent fences retain both
side findings. Messages are:

> Fenced code block requires a blank body line before it.

> Fenced code block requires a blank body line after it.

Full owner context is evaluated before finding-START directive suppression and
inspection focus. Unknown necessary ownership withholds the complete inventory,
including any earlier potential findings, with explicit reduced coverage:

> Fenced-block spacing context is unavailable; the complete MD031 inventory is withheld.

A withheld inventory proves neither suppression use nor complete absence.
Ordinary lint, MD087 observation and requested inactive inspection use the same
analysis. MCP parity remains downstream.

## Configuration

Default enablement: Enabled.

No rule-specific options.

All rules also accept the [shared settings](../index.md#configuration-and-findings). The defaults here are the planned mdchk contract.

## Examples

Violating input:

````markdown
Text
```text
Example
```
````

Accepted input:

````markdown
Text

```text
Example
```
````

Angle-bracket placeholders such as `<SPACE>`, `<TAB>`, `<EOF>`, and `<NEWLINE>` describe source characters rather than literal Markdown. Prose examples describe cases that cannot be represented directly in a UTF-8 document.

## Correction policy

Future work: insert blank lines using the enclosing container's prefixes.
Current findings have no automatic edits, previews or corrected content.

Any correction must satisfy the [shared preservation contract](../index.md#implementation-contract). Report remaining findings after checking the corrected document again.

## Validation

Cover the examples, every option, protected content, nested containers, LF and CRLF input, and precise diagnostic ranges. Current verification includes unchanged source bytes, manual findings, directives,
inspection, source authority and interruption controls. Future corrections must
verify preserved meaning and a second fix run with no further changes.
