# MD009: Whitespace at line ends

Status: CommonMark and GFM analysis and configuration implemented. All findings
are manual; automatic correction remains future work.

Area: [Whitespace](index.md).

## Behavior

Let N be `hard_break_spaces`, an exact count, not a minimum. Lines without trailing whitespace pass in both modes. Exactly N ASCII spaces are allowed with `strict: false`, including at EOF; with `strict: true` they are allowed only for a parser-confirmed hard break. Every other positive space count, trailing tab, or mixed space/tab suffix is reported.

Report whitespace-only lines in both strict modes; there is no hard-break allowance for them. Preserve any parser-owned structural indentation or container prefix when correcting.

By default, code is excluded. With code_blocks=true, report trailing spaces or tabs in literal code without applying a Markdown hard-break allowance. Keep literal-code findings report-only; code_blocks opts into analysis, not modification of code bytes.

Find one maximal physical ASCII space/TAB suffix before the original LF, CRLF,
CR or EOF. Report its entire range, including parser-consumed whitespace, but no
marker or line-ending bytes. No suffix means no finding. Other Unicode whitespace
and NUL are content. Blankness removes only actual consumed list/quote prefixes;
a task checkbox remains content. For example, `> <SPACE>` reports its suffix even
though the quote prefix owns the first space; bare `>` passes.

Strict allowance requires an actual spaces-origin hard-break marker equal to the
whole suffix. A mixed `<TAB><SPACE><SPACE>` suffix reports even when the last two
spaces form a break. A preceding backslash does not veto an actual spaces break.
A terminal paragraph ending, EOF or a block boundary does not invent a break.
Actual GFM table rows have no hard breaks; the same source may be an ordinary
CommonMark paragraph with real breaks on intermediate lines. Reference-definition,
heading, thematic-break and table-delimiter lines remain ordinary candidates.

Code exclusion covers fenced payload, every indented-code contribution (including
blank indentation), and multiline code-span payload. `code_blocks: true` reports
all their positive suffixes, with no numeric allowance. Actual fence opening and
retained closing lines instead use the ordinary numeric policy; unclosed fences
have no guessed closer. A suffix after a code-span closing delimiter is ordinary.

Recognized YAML/TOML headers are protected in full, including delimiter suffixes,
without consuming metadata. Disabled recognition restores Markdown classification;
unterminated recognized headers produce explicit incomplete coverage. HTML blocks
protect their complete owned tails. Inline HTML/comments protect only owned bytes;
a suffix after their closer remains ordinary. Actual semantic raw-tag state also
protects Text/HardBreak bytes between raw open/close tags. Image-description tags
cannot alter enclosing raw state. Protection takes precedence over code opt-in.

See the [complete rule contract](../../engineering/rule-behavior.md).

## Configuration

Default enablement: Enabled.

hard_break_spaces: integer at least 2, 2; strict: boolean, false; code_blocks: boolean, false. Strict mode rejects trailing spaces that do not produce a hard break.

All rules also accept the [shared settings](../index.md#configuration-and-findings). The defaults here are the implemented mdchk contract.

## Examples

Violating input:

````markdown
Text<SPACE>
````

Accepted input:

````markdown
Text
````

With defaults, `Text<SPACE><SPACE><EOF>` passes; `Text<SPACE><EOF>` and
`<SPACE><SPACE><NEWLINE>` report. With strict enabled, both
`Text<SPACE><SPACE><EOF>` and a terminal `Text<SPACE><SPACE><NEWLINE>` report;
`Text<SPACE><SPACE><NEWLINE>next` passes when the parser confirms the break.
For `` `x<SPACE><SPACE><NEWLINE>y`<SPACE><SPACE><NEWLINE>z ``, only the internal
suffix reports with code opt-in; the outside exact-two spaces are a real break.
For `a <script>x<SPACE><SPACE><NEWLINE>y</script><SPACE><NEWLINE>z`, the raw internal
suffix stays protected and the outside one-space suffix reports.

Angle-bracket placeholders such as `<SPACE>`, `<TAB>`, `<EOF>`, and `<NEWLINE>` describe source characters rather than literal Markdown. Prose examples describe cases that cannot be represented directly in a UTF-8 document.

## Future correction policy

For flagged whitespace that currently produces a real hard break, normalize to exactly N ASCII spaces. For other flagged trailing whitespace, remove it only after reparsing confirms preserved interpretation. Never introduce or remove a hard break or change container structure as a side effect. Already permitted whitespace is left alone. Preserve source newline conventions.

Follow the [shared correction contract](../../engineering/fixes.md).

## Validation

Cover the examples, every option, protected content, nested containers, LF and CRLF input, and precise diagnostic ranges. Future correction implementation must separately verify preserved meaning and a second fix run with no further changes. Pass 1 produces no edits, previews, writes or returned corrected content.
