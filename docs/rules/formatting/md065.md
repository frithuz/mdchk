# MD065: Blank lines around horizontal rules

Status: analysis, configuration and correction implemented for CommonMark and
GFM. Eligible findings are fixed; the cases listed under
[Correction policy](#correction-policy) stay manual.

Area: [Formatting](index.md).

## Behavior

Require an immediately adjacent physical blank body line on each nonexempt side
of an actual parsed thematic break. Its immediate Document, BlockQuote or ListItem
body supplies the neighbors; a List only groups items. Retained reference
definitions, including duplicates and multiline definitions, remain source
participants even though they are absent from rendered block children. The first
and last source participant have their respective outward side exempt. Nested
containers and separate items never borrow outside siblings. A recognized opaque
frontmatter header is outside the root body, which starts at its BodyOffset.

Blankness removes only actual prefixes of the owning body and its ancestors.
The remaining original bytes must be empty or ASCII SPACE/TAB. Deeper container
markers, comments, Unicode whitespace and blanks inside opaque neighbors do not
supply outside separation. Lazy lines acquire no invented prefixes, and a final
line ending creates no extra blank line. List-owned trailing blank lines can
supply an outside separator; actual terminal content, empty markers and retained
definitions still determine the preceding participant's boundary.

Code, comments, recognized headers and semantic raw HTML lifetimes do not supply
targets. Actual raw closers and closing tails end protection; image alternatives
retain isolated raw state. Protected blocks still remain neighboring context.
Setext underlines, escaped/entity spellings and marker-looking text are not targets.

Emit one finding per missing side, keeping both observations for a shared
missing gap between adjacent breaks. Exact messages are
`Horizontal rule requires a blank body line before it.` and
`Horizontal rule requires a blank body line after it.` The before point is after
actual owner/ancestor prefixes and before the break's own optional indentation.
The after point is at that line's physical content end, including authored trailing
SPACE/TAB and before the whole LF, CRLF or CR ending. Both ranges are present,
zero-width original-source points with empty slices; shared TAB bytes stay atomic.
For `Text\n***\nMore`, they are [5,5) at (2,1) and [8,8) at (2,4).

Evaluate full source context before filtering each point at its own START for
directives or inspection lines. Disabled neighbors still determine boundaries.
Unreliable required syntax produces reduced coverage. A finding has
`fix_available: true` only when its blank line can be derived and the shared
insertion checks accept it; see [Correction policy](#correction-policy).

## Configuration

Default enablement: Enabled.

No rule-specific options.

All rules also accept the [shared settings](../index.md#configuration-and-findings). Unknown options and invalid shared settings are rejected even when disabled. Omitted settings and an empty mapping use defaults; null is invalid.

## Examples

Violating input:

````markdown
Text
***
More
````

Accepted input:

````markdown
Text

***

More
````

Angle-bracket placeholders such as `<SPACE>`, `<TAB>`, `<EOF>`, and `<NEWLINE>` describe source characters rather than literal Markdown. Prose examples describe cases that cannot be represented directly in a UTF-8 document.

## Correction policy

`mdchk fix` inserts one blank body line on each missing side of a thematic
break. Before a break, the line goes at the start of the break's line. After a
break, it goes at the start of the next line. The inserted line repeats that
line's enclosing container prefixes, with trailing whitespace removed, followed
by the previous line's ending. So `Text<NEWLINE>***<NEWLINE>More` becomes
`Text<NEWLINE><NEWLINE>***<NEWLINE><NEWLINE>More`, a quoted
`> a<NEWLINE>> ***` gets a `>` line between them, and CRLF input gets a CRLF
line.

Two adjacent breaks that share one missing gap get one inserted line, which
fixes both findings.

The correction is accepted only when a reparse of the whole candidate shows the
same blocks and the same thematic breaks, with the same markers and
containers: no break becomes a setext underline, every list keeps its items,
nesting and tightness, no paragraph, list or quote splits or merges, and no
byte outside the inserted lines changes. These findings stay manual, with
`fix_available: false`:

- a finding between two blocks of an item in a tight list, or a list whose
  tightness is unknown, because the new line would make the list loose
- a finding whose neighbouring line is a lazy continuation or has fewer
  blockquote markers than the break's line
- a finding whose container prefix holds anything other than spaces and `>`
  markers, such as a tab
- a finding whose neighbouring line is or touches fenced or indented code, an
  HTML block such as a comment, or front matter
- a finding in a directive interval or protected context, in a document whose
  parse is uncertain, or in a document that opens with an unrecognized `---` or
  `+++` block
- two findings that claim the same inserted line with different contents

MD065 corrections wait for a round with no MD022 or MD032 correction, since a
blank line before a break lands at the same offset as one those rules insert
after a heading or a list. MD023 waits for MD065 in turn, and MD012, MD035 and
the other rules that compare whole parses wait for MD065 as they wait for MD032.
One `fix` run still applies them all.

Any correction must satisfy the [shared preservation contract](../index.md#implementation-contract). Report remaining findings after checking the corrected document again.

## Validation

Cover the examples, every option, protected content, nested containers, LF and CRLF input, and precise diagnostic ranges. For corrections, verify preserved meaning and a second fix run with no further changes.
